# Agent Skill: Glyvio Onboarding

Gets a machine and a plugin project to the point where every other skill works: the
**`@types`** of the project (`glyvio_core.d.ts`, `entity.d.ts`, `permissions.d.ts` and one `.d.ts`
per dependency plugin, in each layer) are generated by the **glyvio-dev-helper** from the
project's `manifest.json`, using the developer's own Glyvio account.

Run the steps in order and stop at the first failure, explaining it to the user.

---

## 🔐 Security rules (NON-NEGOTIABLE)

1. **Never ask for the password in the chat and never print it.** The user types `G_USERNAME` and
   `G_PASSWORD` into `.env` themselves. Do not `cat`/read `.env` back to the conversation; to check
   it, only test whether each key has a value.
2. **`.env` is never committed.** Make sure `.gitignore` contains `.env` *before* the file is created.
   If `.env` was ever committed, tell the user to change the password.
3. Use a personal or development account with access to a development company — never a shared
   production admin account.

---

## 📥 What the user must have

- A Glyvio login (e-mail) and password, and the **company id** of the company used for development
  (ask the company administrator or the Glyvio team if unknown).
- The plugin project: a folder with **`manifest.json`** and **`package.json`** at the root and the
  layers `plugin/app`, `plugin/server`, `plugin/environment`, `shared/commons`.
  - `package.json` → `name` **is the plugin namespace** (the global name its classes live under, e.g.
    `crm`), and `version` its version.
  - `manifest.json` → `dependencies` lists the plugins it builds on; `glyvio_core` is always there
    (skill `modify-manifest`).
  - No project yet? Ask the Glyvio team for the plugin template — this skill does not create one.

## 📋 Steps

### 1. Prerequisites

```sh
node --version   # LTS (20+)
pnpm --version   # if missing: npm install -g pnpm
git --version
```

### 2. Download the glyvio-dev-helper

Base URL: `https://glyvio-public.s3.us-east-1.amazonaws.com/development-support/glyvio-dev-helper/`

| OS | File | Save as |
| --- | --- | --- |
| Windows (x64) | `glyvio-dev-helper.exe` | `tools\glyvio-dev-helper.exe` |
| macOS (Apple Silicon / arm64) | `glyvio-dev-helper-mac` | `tools/glyvio-dev-helper-mac` |
| Linux (x64) | `glyvio-dev-helper-linux` | `tools/glyvio-dev-helper-linux` |

macOS / Linux (in the plugin root):

```sh
mkdir -p tools
curl -fL -o tools/glyvio-dev-helper-linux \
  https://glyvio-public.s3.us-east-1.amazonaws.com/development-support/glyvio-dev-helper/glyvio-dev-helper-linux
chmod +x tools/glyvio-dev-helper-linux
# macOS: use glyvio-dev-helper-mac in both places, then allow the downloaded binary to run:
# xattr -d com.apple.quarantine tools/glyvio-dev-helper-mac
```

Windows (PowerShell, in the plugin root):

```powershell
New-Item -ItemType Directory -Force tools | Out-Null
Invoke-WebRequest -Uri https://glyvio-public.s3.us-east-1.amazonaws.com/development-support/glyvio-dev-helper/glyvio-dev-helper.exe -OutFile tools\glyvio-dev-helper.exe
Unblock-File tools\glyvio-dev-helper.exe
```

Notes:
- The macOS build is **arm64 only**: it does not run on Intel Macs.
- To keep the helper elsewhere (one copy for several plugins), set `GLYVIO_DEV_HELPER` to its full path.
- Run `tools/glyvio-dev-helper-<os> --help` to see the version's options.

### 3. Protect and create the `.env`

Add to `.gitignore` (create it if missing) **before** creating `.env`:

```gitignore
.env
tools/glyvio-dev-helper*
**/@types/*.*
```

Then create `.env` at the plugin root from the template shipped with this skill
(`codex/skills/glyvio-onboarding/assets/env.example`), and **ask the user to fill** the values:

```dotenv
G_APP_URL=https://alpha.glyvio.com
G_AUTH_URL=https://auth-webapi-prod.glyvio.com/
G_COMPANY_ID=
G_USERNAME=
G_PASSWORD=
```

| Key | Meaning |
| --- | --- |
| `G_APP_URL` | The **web app** address (used by browser tests — `test-plugin-browser`). Not used to generate types. |
| `G_AUTH_URL` | Authentication server. A trailing `/` is fine. |
| `G_COMPANY_ID` | Company whose installed plugin versions are used to generate the types. |
| `G_USERNAME` | Glyvio login (e-mail). |
| `G_PASSWORD` | Glyvio password. |
| `G_API_URL` | *Optional.* API address for the generator; leave it out (default `https://webapi-prod.glyvio.com`). **Never** point it to the web app (`G_APP_URL`): the app answers every path with its HTML page. |

Check that the values are filled without showing them:

```sh
for k in G_AUTH_URL G_COMPANY_ID G_USERNAME G_PASSWORD; do grep -q "^$k=..*" .env && echo "$k ok" || echo "$k MISSING"; done
```

### 4. Install `run_helper.sh` / `run_helper.ps1`

Copy both scripts shipped with this skill to the plugin root:

- `codex/skills/glyvio-onboarding/assets/run_helper.sh` → `run_helper.sh` (then `chmod +x run_helper.sh`)
- `codex/skills/glyvio-onboarding/assets/run_helper.ps1` → `run_helper.ps1`

They read `.env` (without executing it), pass the values to the helper as `GLYVIO_*` environment
variables and run it — this works with every helper build, including older ones that do not read
`.env` by themselves. If the project already has a `run_helper.sh`, compare before replacing it.
The scripts contain no secret and can be committed so the whole team uses them.

> Every other skill says "run `./run_helper.sh`" after a manifest change — on Windows that is
> `.\run_helper.ps1`.

### 5. Generate the types

```sh
./run_helper.sh          # macOS / Linux
.\run_helper.ps1         # Windows (PowerShell). If blocked: powershell -ExecutionPolicy Bypass -File .\run_helper.ps1
```

Expected output ends with `Entity DTS generated!`, `Entity Permissions!` and `Dependencies
generated!`, and these files exist (one `.d.ts` per dependency in addition):

```text
plugin/app/@types/{glyvio_core,entity,permissions}.d.ts
plugin/server/@types/{glyvio_core,entity,permissions}.d.ts
plugin/environment/@types/{glyvio_core,entity,permissions}.d.ts
shared/commons/@types/{glyvio_core,entity,permissions}.d.ts
```

The helper **deletes and recreates** the four `@types` folders on every run: never edit those files
and never keep hand-written declarations inside them.

### 6. First build

```sh
pnpm install
pnpm build
```

A clean build means the environment is ready. Run `./run_helper.sh` again whenever `manifest.json`
(entities, fields, permissions, dependencies) changes or a dependency publishes a new version.

## 🩺 Troubleshooting

| Symptom | Cause / fix |
| --- | --- |
| `.env not found` / `fill G_USERNAME and G_PASSWORD` | Step 3 not done, or the script ran outside the plugin root. |
| `run it in the plugin root (manifest.json + package.json)` | Wrong folder, or the project is missing those files. |
| `helper not found or not executable` | Step 2: wrong file name/folder, missing `chmod +x`, or set `GLYVIO_DEV_HELPER`. |
| macOS: "cannot be opened because the developer cannot be verified" / `bad CPU type` | Run the `xattr` command of step 2 / the build is arm64-only (Intel Mac). |
| `answered with an HTML page: it is the web app, not the API` | `G_API_URL` points to the web app — remove it from `.env`. |
| HTTP 401 / 403 | Wrong `G_USERNAME`/`G_PASSWORD`, or the user has no access to `G_COMPANY_ID`. |
| `File not found: .../package.json` | Create it with `name` = plugin namespace and `version`. |
| `Multiples versions of plugin (...) found` | Two dependencies require different versions of the same plugin; align `manifest.json` (or use `dependenciesOverride`). |
| `Entity name X is too big` | Entity/field names over the generator limits (skill `modify-manifest`, rule 6). |
| Types of a dependency are missing | Add it to `dependencies` in `manifest.json` and run the helper again. |
